- [X] 子任务 2：导航体验——桌面端导航链接增加"从中心展开"下划线动效；滚动时自动高亮当前区块对应的导航项（scroll-spy）；向下滚动自动隐藏导航栏、向上滚动恢复显示（移动端菜单展开时不触发隐藏）。
- [X] 子任务 3：联系弹层——三个渠道选项进场时错落浮现（stagger，逐项清除内联延迟避免影响后续 hover）；支持方向键 ↑/↓ 在选项间移动焦点；新增拖拽把手，移动端支持从顶部下滑手势关闭弹层；遮罩增加轻微 `backdrop-filter` 模糊质感。
- [X] 子任务 4：滚动细节——重写 `initScrollReveal`，按"同一父元素下的兄弟节点"自动分组并计算错落延迟，让 Services 五行、Process 三步在进入视口时依次错开出现，而不是整块一起淡入。
- [X] 子任务 5：移动端手势——移动导航菜单支持点击外部区域关闭、支持 Esc 键关闭并将焦点归还给汉堡按钮。
- [X] 子任务 6：排查一次"headless 截图下大片内容看似消失"的诡异现象，通过诊断脚本确认根因是"headless + URL 锚点直达 + 虚拟时间预算"组合下的滚动时序问题（scrollY 已跳转到锚点位置，只是截图视口恰好落在两段内容之间的空白处），并非代码 bug；随后用真实浏览器加载验证，首屏、Services、联系弹层等区域全部渲染正常，导航栏在正常滚动场景下工作正确。

### 总结
- 本轮新增的交互全部通过"独立属性通道"设计，避免了"进场动画的 `transform`/`opacity` 过渡"与"hover 反馈的 `transform`/`opacity` 过渡"共用同一 CSS 属性导致的过渡延迟互相污染问题（例如：联系选项的入场用 `opacity+transform`，hover 反馈改用 `border-color+background`，避免了两者抢用同一属性）。
- 错落进场（stagger）没有用 CSS `nth-child` 写死延迟，而是用 JS 动态计算并在动画结束后清除内联 `transition-delay`，这样"进场时错落、进场后 hover 依然灵敏"两者可以兼得。
- 再次印证了 `Lesson.md` 里记录的经验："headless + URL 锚点跳转"的组合在做视觉验证时不可靠，遇到看似诡异的"内容消失"现象时，应该先用诊断脚本打印真实的 `scrollY`/`computedStyle`，而不是直接怀疑代码逻辑；最终仍以真实浏览器渲染结果为准。

### 目标
客户反馈移除"滚动隐藏"效果后，导航栏仍然会因为滚动而消失，要求导航栏彻底固定在顶部、与下方可滚动内容完全隔绝。

### 计划
- [X] 子任务 1：排查根因——确认是 `position: sticky` 配合 `html`/`body` 上的 `overflow-x: hidden` 在部分滚动场景下的已知兼容性问题，而不是遗留的 JS 逻辑。
- [X] 子任务 2：把 `.nav` 从 `position: sticky; top: 0;` 改为 `position: fixed; top: 0; left: 0; right: 0;`，让导航栏彻底脱离文档流、固定于视口。
- [X] 子任务 3：给 `body` 补上 `padding-top: var(--nav-height);`，把导航栏原本在文档流里占用的空间还回来，避免 Hero 等内容被遮挡或出现多余空白。

- [X] 子任务 5：Lint 检查通过，清理测试文件，更新工作日志。

### 总结
- `position: sticky` 虽然平时表现良好，但在页面同时存在 `overflow-x: hidden` 这类"隐性滚动容器"因素时，稳定性不如 `position: fixed`；对于承载核心导航和主 CTA 的元素，宁可多写一行 `padding-top` 做补偿，也应该优先选择行为更确定的 `fixed`。
- 这类"贴顶失效"问题很难通过静态截图复现（截图往往只在滚动前拍一张），真正验证需要结合真实滚动交互或至少推理清楚浏览器的定位计算规则，不能只看"看起来对不对"。

- [X] 子任类 3：把手机/平板条带（现在覆盖到 1024~1249px）的横向摆动幅度也从固定 px（26/24/20px）改成 vw 自适应加上限（`min/max(CAPpx, Xvw)`），以常见手机宽度 400px 为基准换算，保证真手机上的观感不变，扩大后新覆盖到的平板宽度不会显得摆动幅度小得不成比例。
- [X] 子任务 4：用 CDP 在 1250/1300/1366/1440/1600/1920/2560（桌面）与 360~1249（手机/平板条带）两套宽度矩阵上分别验证：全部 0 裁切；额外统计"每个宽度下，离视口真实边缘最近的水印边缘还差多少像素"这个指标，确认这个数值稳定维持在 40~115px 之间（而不是像修复前那样从几十涨到 500+px），证明留白问题已经解决。

- [X] 子任务 6：清理全部临时测量/验证脚本、Edge 临时用户目录、截图。
- [X] 子任务 7：更新 `README.md`、工作日志。

### 总结
- "按固定基准宽度换算出一个 vw 比例"和"让某个量始终占用某块可用空间的固定比例"是两件不同的事——前者在偏离基准宽度越远时误差越大，后者才能真正做到"随便多宽的屏幕都用满这块空间"。这次的教训是：调完之后不能只满足于"这个宽度不裁切"，还要专门去量"用了多少可用空间、还剩多少没用上"，才能发现"没裁切但没用满"这类不明显的问题。
- 有了"精确测量文字真实宽度"的方法（CDP + `getBoundingClientRect().width`）之后，很多之前靠"字符数 × 估算单字宽度"做的取舍（比如为了防裁切统一把文案剪短到 20 字符以内）都可以更精确地重新核算，不用再靠经验值留一大截安全冗余。
