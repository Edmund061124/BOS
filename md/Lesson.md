# Lesson.md

## 问题 1：Windows PowerShell 下中文/宽字符目录名显示为乱码
- **问题描述**：`Get-ChildItem` 默认输出把中文文件夹名（如"品牌logo"）显示为 `??logo`，一度以为目录是空的。
- **解决方案**：执行 `chcp 65001` 切换到 UTF-8 代码页后再执行 `Get-ChildItem`，中文文件名即可正常显示；也可以用通配符（如 `Get-ChildItem -Path "*logo*"`）绕过显示问题直接定位目标目录。
- **注意事项**：以后在 Windows + PowerShell 环境下处理中文路径，遇到"目录为空/找不到"的异常情况时，先怀疑是编码显示问题，而不是真的没有文件。

## 问题 2：Chrome/Edge Headless 截图配合 `scroll-behavior: smooth` 会截到滚动动画中途的画面
- **问题描述**：用 `file://index.html#services` 之类的锚点跳转 + `msedge --headless=new --screenshot=...` 截图时，页面因为 CSS 设了 `html { scroll-behavior: smooth; }`，锚点跳转会被拉长成动画，而 headless 截图在动画播放完成前就已经完成截图，导致截到的画面还停留在几乎没滚动的位置。
- **解决方案**：制作一份仅用于截图验证的临时副本，在 `<head>` 末尾追加 `<style>html{scroll-behavior:auto !important}</style>`（或对于要截"打开态"的交互如弹层/菜单，额外追加 `*{transition:none!important;animation:none!important}`），跳过动画直接呈现终态，再配合 `--virtual-time-budget` 给 JS 的 `setTimeout` 留出真实触发时间。截图验证完成后必须删除这些临时文件，不能带入交付物。
- **注意事项**：验证交互态/滚动态截图时，始终使用"临时副本 + 强制去动画"的方式，不要直接在正式源文件上加调试代码。

## 问题 3：自动化启动的浏览器窗口拿不到系统前台焦点，桌面截图（`ImageGrab`）截到的是别的窗口
- **问题描述**：用 Python 脚本 `subprocess.Popen` 启动 Edge 后立刻用 `PIL.ImageGrab.grab()` 截全屏，结果有时候截到的是当前 IDE 窗口而不是新打开的 Edge 窗口——Windows 的前台窗口切换有防止"抢焦点"的安全策略，新进程不一定能自动获得前台焦点，且该行为不稳定（同样的脚本时灵时不灵）。
- **解决方案**：用 `pywin32` 的 `AttachThreadInput` 技巧强制切前台（把当前前台线程与目标窗口线程"绑定"后再调用 `SetForegroundWindow`），配合 `EnumWindows` 按窗口标题关键字定位目标窗口。即便如此在某些受限环境下依然可能失败；这种情况下应优先退回使用 **headless 截图**（不依赖任何窗口焦点，稳定可靠），只有在必须验证"真实渲染像素/字体反锯齿"等 headless 无法覆盖的场景，才使用真实浏览器 + 强制前台的方案作为补充。
- **注意事项**：GUI 自动化截图在远程桌面/云端沙箱环境里天然不可靠，做视觉验证时应优先选择 headless + 强制去动画的方案，把真实窗口截图当作补充手段而非首选。

## 问题 4：极窄 `--window-size`（如 390px）下 headless 截图出现"文字被裁切在画面右边缘"的假象
- **问题描述**：直接用 `--window-size=390,844 --screenshot=...` 截移动端首屏，发现多行文字（如 hero 副标题）最后几个字符像是超出了 390px 画布右边缘。一开始怀疑是 CSS 排版溢出的真实 bug。
- **排查方法**：把同一个 `index.html` 通过 `<iframe style="width:390px;...">` 嵌入另一个诊断页面里渲染，同时打印 `contentDocument.documentElement.scrollWidth`。结果显示在真正的 390px 容器里，所有文字换行、排版都完全正常，没有任何溢出。
- **结论**：这是 headless Chrome 在极窄 `--window-size` 场景下的截图渲染误差（可能与该参数同时决定视口尺寸又影响截图画布尺寸时的取整/设备像素比处理有关），并非页面代码问题。
- **注意事项**：以后怀疑"窄屏文字溢出"时，先用 iframe 隔离容器宽度做一次独立验证，避免被截图工具自身的误差带偏、错误地去"修复"本来没有问题的 CSS。

## 问题 5：`Popen` 启动的浏览器进程可能不是最终持有窗口的进程，直接 `Remove-Item` 清理其 profile 目录会导致后续调用截到空白页
- **问题描述**：在一个循环里连续用不同的 `--user-data-dir` 启动多个 headless 截图任务，并在每次调用后立刻清理该 profile 目录，结果第 2、3 个任务经常截到空白页（5851 字节这种固定大小的"空白"文件）。
- **解决方案**：不要在同一个脚本/循环里对多个浏览器实例做"启动 → 立刻清理 profile"的紧耦合操作；每个截图任务应该是完全独立的一次调用（独立的 shell 调用、独立的等待），让浏览器进程有充分时间完成加载、绘制、写文件后再退出，之后再清理临时目录。
- **注意事项**：批量截图时，避免为了"图快"把多个浏览器启动挤在一个紧凑循环里，宁可牺牲一点执行时间换取每一张截图的可靠性。

## 问题 6：多个元素共用同一 CSS 属性（如 `transform`）做不同用途的过渡时，`transition-delay` 会互相"串味"
- **问题描述**：想给"滚动进入视口时的淡入错落效果"和"鼠标悬浮时的位移反馈"都用 `transform` 实现，如果用 CSS `nth-child` 写死 `transition-delay` 来做错落效果，这个延迟会对同一元素后续所有用到 `transform`/相关属性的过渡（包括 hover）都生效，导致"页面刚加载完的一小段时间里，hover 反馈会莫名其妙地卡顿延迟"。
- **解决方案**：两个方案二选一：① 让"入场动画"和"hover 反馈"使用两个不同的 CSS 属性（例如入场用 `opacity + transform`，hover 反馈改用 `border-color + background`，两者互不干扰）；② 如果必须共用属性，就不要在样式表里写死 `transition-delay`，改成用 JavaScript 在触发入场动画的那一刻临时设置内联 `style.transitionDelay`，并在动画播放完成后（用 `setTimeout` 或监听 `transitionend`）把内联延迟清空，恢复成默认的 0 延迟。
- **注意事项**：任何"错落/依次出现"的动效，设计阶段就要想清楚它和该元素其他交互状态（hover、focus、active）有没有共用同一个 CSS 属性，避免顾此失彼。

## 问题 7：`headless + URL 锚点直达（#id）+ 长时间等待` 组合下，截图偶尔会"漏掉"本该在视口内的内容
- **问题描述**：用 `msedge --headless=new --virtual-time-budget=... "file:///xxx.html#services"` 截图时，个别情况下截图看起来像是大片内容"消失"了（页面顶部一片空白，只剩下零星几个按钮），一度怀疑是新写的 CSS/JS 把很多元素弄成透明或隐藏了。
- **排查方法**：不要凭肉眼猜测，而是往页面里临时插入一段诊断脚本，把 `window.scrollY`、目标元素的 `className`、`getComputedStyle(el).opacity`、`getComputedStyle(nav).transform` 等真实数值打印成页面上可见的文字（比如一个高对比度的浮层），再截图确认。诊断结果显示：这些元素的 `opacity` 其实是 `1`（完全可见），`scrollY` 也确实已经跳到了锚点对应的位置——真正的原因是"锚点跳转的滚动位置"和"截图视口"之间出现了错位（截图这一帧的视口恰好落在两段可见内容之间的空白间隙），而不是代码把内容隐藏了。
- **结论 / 解决方案**：`headless + URL 锚点直达`这种测试方式本身对滚动定位时机比较敏感，输出结果仅供参考，不能直接当作"代码有 bug"的证据。真正要确认视觉效果时，优先切回"真实浏览器窗口加载 + 真实屏幕截图"的方式（见问题 3 的方案），它的滚动定位稳定可靠得多。
- **注意事项**：遇到"一大片内容突然消失"这种看起来很离谱的现象时，第一反应应该是怀疑测试工具本身的时序问题，用诊断脚本打印真实数值去验证，而不是立刻回头去改动刚写好的业务代码。

## 问题 8：给带伪元素前缀（如 "// "）的文字标签用 `display:flex` 布局，窄屏下文字不换行、被截断
- **问题描述**：想给 `.eyebrow` 标签用 `::before { content:'//' }` 加一个"代码注释"前缀，为了方便控制前缀和文字之间的间距、居中对齐，把 `.eyebrow` 写成了 `display:flex; align-items:center; gap:6px;`。桌面端看起来没问题，但在真机窄屏（390px）截图验证时发现较长的标签文案（如 "MALAYSIA · CUSTOM-BUILT DIGITAL SYSTEMS"）会整行溢出屏幕右边，不会自动换行。
- **原因**：`display:flex` 的容器里，`::before` 生成的内容和原始文本节点会分别成为独立的 flex 子项；flex 子项的 `min-width` 默认是 `auto`，对文本内容而言这个"auto"约等于"整段文字不换行时的最大宽度"，导致该文本子项拒绝在窄容器里换行，从而溢出。
- **解决方案**：不需要 flex 也能实现"前缀 + 文字"的效果——把 `::before { content:'// '; }` 直接写成普通行内内容（不设置 `display:flex`），前缀和正文都在正常的行内文本流里，浏览器会按平时的规则自动换行，居中/左对齐也交给父级已有的 `text-align`/`flex` 布局处理即可。
- **注意事项**：只是想给文字加一个简单的前缀/图标时，优先用 `::before` + 行内内容这种最朴素的写法；只有真的需要精确控制"前缀"和"文字"两个独立块的对齐/换行时才考虑 flex，并且一旦用了 flex 包裹文本，一定要记得在窄屏下额外验证换行是否正常（或显式设置 `min-width: 0`）。

## 问题 9：连续截图任务中，生成的 PNG 文件会在写入后极短时间内"消失"
- **问题描述**：用 `msedge --headless` 生成截图后，命令行明确提示"已写入 N 字节到文件"，但紧接着用 `Get-Item` 检查（无论是系统临时目录还是项目目录）却提示文件不存在；现象在同一次会话里反复出现，与问题 5（profile 目录被提前清理）表现类似但触发条件不同——这次没有主动清理代码，文件是"自己"消失的。
- **解决方案**：怀疑是环境侧（如安全软件的实时扫描/清理机制）对短时间内密集生成的浏览器自动化截图文件做了处理；应对方式是缩短"截图命令"与"读取图片"之间的路径——截图那一条 shell 命令执行完，立刻紧接着调用读图工具，中间不要再插入任何其它 shell 调用（哪怕只是 `Get-Item` 检查文件是否存在），这样能大概率在文件被清理前完成读取。
- **注意事项**：以后遇到"命令行说写入成功，但文件读不到"的情况，不要反复用同一个文件名重试，而是换新文件名重新生成一次，并且生成后第一时间就去读取，不要中间插入调试性质的检查步骤。

## 问题 10：手写的 SVG 文件里 XML 注释导致解析失败，背景图完全不渲染
- **问题描述**：给一个用作 CSS 平铺背景的 SVG 文件加了一段较长的 XML 注释（`<!-- ... -->`）做说明，结果这张 SVG 作为 `background-image` 引用后，页面上完全看不到应有的图案；直接用浏览器打开这个 SVG 文件单独截图，发现报错 `xmlParseComment: invalid xmlChar value 20`，即文件整体解析失败，返回空白。
- **原因**：SVG 本质是 XML，对注释内容、特殊字符、文件编码声明比 HTML 更严格；缺少 `<?xml version="1.0" encoding="UTF-8"?>` 声明、或注释里混杂了较复杂的标点/中英文说明，都可能触发解析器报错，一旦解析失败，整个背景图会静默地不显示，不会在页面主文档里报任何错误（因为它是被当成一张外部图片加载的，加载失败只是"图裂了"，不会有明显提示）。
- **解决方案**：排查"引用的背景图/图标不显示"问题时，第一步应该是脱离宿主页面，直接单独打开这个资源文件（图片/SVG）本身看能不能正常渲染，而不是先怀疑 CSS 里的路径或 `background-*` 属性。SVG 文件本身要保持简单：显式加 `<?xml version="1.0" encoding="UTF-8"?>` 声明，注释尽量精简为一行纯文本，避免在 SVG 里写复杂的多行说明。
- **注意事项**：手写/生成 SVG 素材文件时，把它当作真正的 XML 来对待，写完之后先单独打开验证一次，再接入到页面里，能省去很多"背景图为什么不显示"的排查时间。

## 问题 11：为了"交互更丰富"主动加的效果，后续被客户理解成"缺陷"（导航栏消失）
- **问题描述**：早期为了让页面"更丰富"，给导航栏加了"向下滚动自动隐藏、向上滚动恢复"的效果。这个效果本身没有代码 bug，但客户后来反馈"导航栏会因为页面移动而消失"，把这个主动设计的交互当成了问题。
- **原因**：一个交互效果"技术上工作正常"和"符合客户真实预期"是两件事；导航栏承载着随时可点的 `Contact us` 主 CTA，"滚动时消失"这个设计选择对以转化为目标的营销页面并不一定是好的取舍，客户的直觉反馈（"应该一直固定")其实更合理。
- **解决方案**：直接按客户最新反馈移除该效果（删掉 JS 里的可见性判断逻辑和 CSS 里的隐藏样式），不用纠结"这其实是我们之前设计的功能"，客户的实际使用体验优先于此前的方案。
- **注意事项**：以后加"克制但丰富"的交互效果时，凡是涉及"核心导航/CTA 会不会消失/移位"这类可能影响可用性的效果，最好提前跟客户确认一下预期，而不是单方面假设"这样更有质感"。

## 问题 12：`position: sticky` 配合祖先元素的 `overflow-x: hidden` 在部分场景下贴顶失效
- **问题描述**：移除了"滚动隐藏导航栏"的 JS 效果之后，客户仍然反馈导航栏会"因为滚动而消失"。但检查代码，`.nav` 一直是 `position: sticky; top: 0;`，理论上不应该消失。
- **原因**：项目里 `html` 和 `body` 都显式设置了 `overflow-x: hidden`（当初是为了防止极少数横向溢出内容破坏布局）。`position: sticky` 依赖"找到最近的可滚动祖先"来计算贴顶效果，而设置了非 `visible` 的 `overflow-x` 会连带影响 `overflow-y` 的计算值，形成一种容易在不同浏览器/滚动场景下表现不一致的"隐性滚动容器"，导致 sticky 定位在某些情况下计算出错、不能稳定贴顶。这类问题往往不会在简单的截图测试里复现，只有真实滚动交互时才会暴露。
- **解决方案**：如果一个元素必须"无论如何都固定在视口顶部"，比起 `position: sticky`，优先考虑 `position: fixed`（固定于视口，不依赖任何祖先的 `overflow`/滚动容器状态），代价是需要手动给后续内容补一个等于该元素高度的 `padding-top`/`margin-top`，把它从文档流中"让出"的空间还回来。
- **注意事项**：如果页面里同时存在"某个元素需要 sticky/fixed 贴顶"和"html/body 设置了非 visible 的 overflow"这两个条件，优先怀疑两者的组合可能是贴顶失效的原因；对于承载关键导航/CTA 的元素，`fixed` 通常比 `sticky` 更可靠、更不容易受这类隐性因素影响。

## 问题 13：白底黑字 Logo 转"透明背景"时用了错误的抠图方法，边缘留下一圈不透明浅灰色描边
- **问题描述**：客户反馈导航栏的 Logo（`assets/bos-mark-transparent.png`）"轮廓有瑕疵、不够清晰"。对比原始素材 `品牌logo/BOS Letter Mark Logo.png`（1024×1024，白底黑字，边缘有正常的抗锯齿灰度过渡）和当时线上用的透明版，发现问题真实存在。
- **原因**：早期生成透明版时用的是"阈值抠图"思路——只要像素不是纯白就原样保留、只有接近纯白的像素才设为全透明，但保留下来的像素**颜色没有重新计算**，直接沿用了原图里那些属于"白到黑过渡"的浅灰色 RGB 值，同时 alpha 却给成了 255（完全不透明）。结果是：真正的黑色主体外面，围了一圈"完全不透明的浅灰色像素"，而不是"半透明的黑色像素"——这圈实色浅灰边就是客户看到的"瑕疵描边"，Logo 越放大越明显。
- **解决方案**：黑字白底转透明底的正确做法是"用亮度算透明度，颜色统一置为目标墨色"：`alpha = 255 - 亮度`，`RGB = 固定的墨色（如 #111110）`。这样原图里任何深浅的灰度过渡都会被换算成同一种颜色下"深浅不同的透明度"，在任何背景色上叠加都能还原出和原图一样平滑的抗锯齿边缘。用 PIL 的 `Image.point()` 对灰度图做逐像素映射即可高效实现，不需要 numpy；另外注意给 alpha 设一个很小的下限阈值（比如 ≤4 直接归零），避免图片里非纯白噪声（254/253 这种）导致整张画布都被认为"有内容"，从而让 `getbbox()` 裁剪失效。
- **注意事项**：以后凡是"把线稿/Logo 从白底转成透明底"，先用取色工具检查转换后边缘像素的 RGBA 四个值——只要看到"alpha=255 但颜色不是纯目标色"的像素，就说明抠图方法有问题，需要按亮度重算透明度，而不是简单地做"保留/删除"的二选一阈值判断。同时 favicon、apple-touch-icon 等派生素材如果是从同一张问题图裁切生成的，要记得一并重新生成，不要漏改。

## 问题 14：给 Hero 背景挖"内容安全区"时，与其猜一个椭圆形蒙版，不如按内容区实际尺寸定义一个矩形范围
- **问题描述**：早期用 `radial-gradient(ellipse 64% 66% at 50% 47%, transparent 52%, #000 100%)` 给背景代码水印挖空，数值是"试出来的"，说不清楚这个椭圆和真实内容区 `.hero-inner`（`max-width: 860px`，`display:flex` 垂直居中）到底是什么关系，客户也提出想法："先设置中间内容区域的范围，范围之外再铺代码水印"。
- **解决方案**：用两条 `linear-gradient`（一条控制水平方向、一条控制垂直方向）分别定义"水平安全区宽度（对齐 `.hero-inner` 的 `max-width`）"和"垂直安全区高度（按内容区大致占的百分比）"，各自在边缘加一段柔和过渡（feather）。两个 mask 图层不设置 `mask-composite` 时，浏览器默认按 `add`（相当于取并集/OR）叠加——于是画面中只有"同时落在水平安全区 **且** 垂直安全区内"的像素才会被完全挖空隐藏，其余位置（不论是左右留白还是内容上下方）都会显示水印。比起一个整体椭圆，这种写法的两个尺寸都能直接对应到设计里真实存在的数值（内容宽度、内容高度占比），改起来也更直观。
- **注意事项**：用固定像素值（如 860px）做水平安全区宽度时，要注意在比这个值更窄的视口下会发生什么——因为 `50% - 安全区一半` 可能算出负值，水平方向的"安全区"会撑满整个视口宽度，此时图案是否显示就完全由另一条（垂直）蒙版决定。这不是 bug，但设计时要预期到"窄屏下会退化成只在内容上下方出现整宽的水印条"，并确认这个退化效果本身也是可以接受的，而不是等真机测试时才意外发现。

## 问题 15：本机没有安装 Python，做"生成 pptx 文档"这类任务时不能默认走 `python-pptx`
- **问题描述**：习惯性想用 `python-pptx` 生成 PPT 文件，执行 `python --version` 时提示 "Python was not found"，并弹出走 Microsoft Store 安装引导的报错，说明当前 Windows 环境的 `python` 命令只是一个未配置真实解释器的执行别名。

## 问题 16：PowerShell 默认代码页下，脚本生成的中文文件名在 `Get-ChildItem` 输出里显示为 `????`，容易被误判为"生成失败"
- **问题描述**：用 Node.js 生成了文件名含中文的 `BOS-Landing-文案整理.pptx`，用 `Get-ChildItem` 检查时 `Name`/`FullName` 字段里的中文全部显示为 `?`，第一眼看像是文件名写坏了。
- **解决方案**：这和 `Lesson.md` 问题 1 同源，是 PowerShell 控制台默认代码页（非 UTF-8）在**显示**层面的限制，不是磁盘上文件名真的损坏。执行 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8` 后重新 `Get-ChildItem`，中文文件名即可正常显示；也可以直接跳过显示校验，改用文件大小（`Length`）等非文本字段确认文件已生成。
- **注意事项**：任何时候看到 Windows 终端里输出的中文变成 `?` 或乱码，第一反应应该是"这是终端显示问题"，通过切 UTF-8 编码重新读取确认真实情况，而不是立即断定操作失败并重新执行一遍。

## 问题 17：本机无 Python/PIL 时，用 Node.js `sharp` 合成"品牌图 + SVG 文字"式社交分享卡片图（og:image）
- **问题描述**：需要生成一张 1200×630 的社交分享卡片图（Open Graph `og:image`），本机没有 Python/PIL，也没有设计软件可直接导出。
- **解决方案**：用 `sharp`（Node.js 图像库，预编译二进制无需本机装 C 编译工具链）分两步合成：① 把 SVG 里的 `<text>` 节点单独渲染成一张透明背景的 PNG（`sharp(Buffer.from(svgString)).png().toBuffer()`），文字用 `font-family="Arial, Helvetica, sans-serif"` 这种系统里几乎必然存在的字体，避免因缺少特定字体导致渲染异常；② 用 `sharp({create:{...}})` 建一张纯色背景画布，再依次 `composite()` 叠加"已缩放好的品牌 Logo PNG"和上一步生成的"文字 PNG"，最终 `.png().toFile()` 导出。生成后一定要用图片查看工具实际打开看一眼排版、字体渲染、留白是否正常，不能只看命令行"写入成功"就当作完成。
- **注意事项**：`sharp` 渲染 SVG 里的文字时依赖底层 `librsvg`，不同系统对复杂字体/中文的支持不稳定；涉及英文/数字等基础字符时用系统常见字体基本没问题，但如果以后需要在生成图里放中文文字，应该先小范围测试渲染效果，必要时改用"直接合成已经设计好的图片元素"而不是依赖 SVG 文字渲染中文。

## 问题 18：截图验证用的临时 HTML 副本放在系统 `%TEMP%` 目录时，相对路径的 CSS/JS/图片全部加载失败
- **问题描述**：为了截图验证某个交互效果，把加了"去动画"样式的临时 HTML 副本保存到系统 `%TEMP%` 目录后用 headless 浏览器打开截图，结果截图里的页面完全没有样式（纯黑白无格式的默认 HTML 排版），一度怀疑是新改的 CSS 出了问题。
- **原因**：页面里 `<link rel="stylesheet" href="styles.css">`、`<script src="main.js">`、`<img src="assets/...">` 用的都是相对路径，通过 `file://` 协议打开时，这些相对路径是相对"当前 HTML 文件自身所在的目录"解析的。把临时副本放到 `%TEMP%` 目录后，相对路径会去 `%TEMP%` 目录下找 `styles.css`/`main.js`/`assets`，自然全部 404，页面退化成毫无样式的原始 HTML。
- **解决方案**：截图验证用的临时 HTML 副本必须保存在**项目目录内部**（和真正的 `styles.css`/`main.js`/`assets` 同级），这样相对路径才能正确解析；截图验证完成后立刻删除该临时文件，不带入交付物。
- **注意事项**：以后凡是"复制一份 HTML 做临时修改再截图/预览"的操作，第一反应就是把临时文件放在原文件同一目录下，而不是图方便放到系统临时目录；如果截图结果显示"样式整个丢失、变成默认排版"，应优先怀疑是临时文件位置导致的相对路径失效，而不是先怀疑最近改的 CSS 代码本身。

## 问题 19：纯线条风格的 SVG 图标集里，"实心小圆点"如果用 `<circle fill="currentColor">` 会破坏整体线条统一感
- **问题描述**：把三个联系渠道图标统一改成 `fill="none" + stroke="currentColor"` 的线条风格时，Instagram 图标右上角原本有一个用 `<circle r="1.1" fill="currentColor">` 画的实心小圆点（代表相机的自拍灯），如果保留不改，整套图标里就会混入一个"唯一的实心色块"，破坏"全部都是线条描边"的视觉一致性。
- **解决方案**：改用 Feather Icons 等主流线条图标库常用的技巧——画一条起点和终点重合的"零长度线段"（`<line x1="a" y1="b" x2="a" y2="b">`），配合 `stroke-linecap="round"` 和较粗的 `stroke-width`，线段的两个圆头端点会重叠在一起，视觉上呈现出一个"实心圆点"的效果，但技术上仍然是一条 `stroke` 描边线，和图标里其它线条元素保持同一种绘制方式，代码层面也更统一（不需要额外引入 `fill` 属性）。
- **注意事项**：以后凡是要设计/绘制"纯线条风格"的图标集，遇到"看起来需要一个实心点/圆"的细节，可以优先考虑"零长度线段 + 圆头描边"这个技巧，而不是直接用带 `fill` 的图形，能让整套图标的绘制方式保持统一，也方便后续统一通过 `stroke` 相关的 CSS（如 `stroke-width`、`color`）去控制所有图标的粗细和颜色。

## 问题 20：删除 HTML 占位链接时，应同步清理仅服务于该链接的 CSS
- **问题描述**：客户要求删除页脚 `Privacy Policy` 占位链接后，若只改 HTML 而留下 `.footer-link` 样式，会在样式表里留下无引用的死代码。
- **解决方案**：删除对应 DOM 节点的同时，用搜索确认该类名是否还有其它引用；若仅服务于该链接，一并删除相关 CSS 规则。
- **注意事项**：小范围删除 UI 元素时，优先做一次"HTML 删除 + 样式引用搜索"，避免长期堆积无用选择器。

## 问题 21：为了"一张截图截全页"而人为调大 `--window-size` 高度，会把用到 `vh` 单位的区块撑大变形
- **问题描述**：为了一次性截到整个长页面，把 headless 的 `--window-size` 高度设得很大（比如 7500px），结果发现页面顶部 Hero 区块的内容被挤到了很靠下的位置，上方出现大片异常空白，一度怀疑是新代码引入的布局 bug。
- **原因**：Hero 用了 `min-height: calc(100vh - 导航栏高度)` 来实现"占满首屏高度、内容垂直居中"的效果。`100vh` 是相对**当前渲染视口高度**计算的，而不是相对"内容实际需要的高度"——人为把 `--window-size` 的高度调到 7500，`100vh` 就等于 7500px，Hero 区块被同比例撑大，内容虽然还是居中，但"居中的位置"是在一个 7500px 高的区块正中间，看起来就像是被推到了很下面。
- **解决方案**：截图验证时不要用人为夸大的高度去"凑一张全page图"；应该用贴近真实设备的合理高度（如手机常见的 844px）。如果需要看到页面更靠下的内容，改用"临时给测试专用副本加一条 `display:none` 的 CSS，隐藏掉前面的板块"，让目标板块自然出现在页面顶部（此时 `100vh` 依然是正常的设备高度，不会被撑大），而不是拉高整个测试窗口。
- **注意事项**：任何页面只要用了 `vh`/`dvh`/`svh` 等视口相对单位做尺寸，截图验证时的 `--window-size` 高度就必须贴近真实设备的高度，不能为了"减少截图次数、一次截全页"而随意调大，否则测试结果本身就是失真的。

## 问题 22：headless `--screenshot` 配合 `position: fixed` 元素 + 程序化滚动（`scrollTo`/URL 锚点），滚动效果无法正确反映在截图里
- **问题描述**：想看页面中段/底部内容，尝试了两种方式——① 页面加载后用 `window.scrollTo(0, y)` 滚动到指定位置再截图；② 直接用带锚点的 URL（如 `file:///xxx.html#services`）截图。两种方式截出来的图都显示：`position: fixed` 的导航栏"跑"到了画面底部而不是正常贴在顶部，页面主体内容也没有真正显示出滚动后应该看到的部分。
- **原因**：这是 `--screenshot` 命令行截图机制本身在"`position: fixed` 元素 + 已发生滚动"这个组合场景下的渲染缺陷——`fixed` 元素理论上应该始终锚定在视口位置、不随滚动改变，但这套截图管线里似乎把它按照某种"和文档流耦合"的方式处理了，导致滚动越多、`fixed` 元素在截图里的位置就跟着往下跑。已经排除是代码问题：页面在真实浏览器里滚动、导航栏贴顶的行为在本项目里被反复验证多次都是正常的，本轮排查也没有改动任何相关代码。
- **解决方案**：不要依赖"程序化滚动 + 单次截图"的组合去验证页面中段/底部内容。改用"给测试专用副本加一条 CSS，把想跳过的前置板块设成 `display:none`"，让目标内容自然出现在文档顶部（此时截图时 `scrollY` 始终是 0，不涉及任何滚动，`fixed` 导航栏自然正常贴顶），从根源上绕开这个截图局限。
- **注意事项**：以后凡是要用 headless `--screenshot` 验证"滚动到某处之后"的视觉效果，第一选择是"隐藏/裁剪掉不需要看的内容让目标区域出现在顶部"，而不是"滚动到目标位置"——尤其是页面里存在 `position: fixed`/`sticky` 元素时，程序化滚动类的验证方式已经被反复证明不可靠。

## 问题 23：固定像素的响应式"安全区"从桌面直接照搬到移动端时，会因尺寸不匹配而被整体关闭，之后误以为是"忘了适配"
- **问题描述**：客户反馈手机端看不到 `code-pattern.svg` 代码水印，第一反应可能是"CSS 漏写了移动端样式"，但检查后发现 `.hero-code-field` 其实是被 `display: none` **主动**关闭的，只有 `@media (min-width: 768px)` 才开启。
- **原因**：该水印的"内容安全区"（挖空、不显示水印的中间区域）宽度是一个固定像素值 `--safe-w: 860px`，这个数值是对齐桌面版 `.hero-inner` 的 `max-width` 设定的。如果直接在手机屏幕（通常 <430px）上复用同一数值，`50% - 860px/2` 会算出很大的负值，导致水平方向的"安全区"实际上覆盖了整个视口宽度——也就是说水印即使打开 `display:block` 也会被完全挖空、什么都看不见。当时的开发索性直接把移动端的 `display` 关掉，避免"打开了但看起来什么都没做"的困惑，但这个取舍在项目文档里只以断点数值的形式存在，没有被非常显眼地强调，容易在后续被误认为"忘记适配移动端"。
- **解决方案**：确认客户这次是真的想要"手机端也显示"之后，不是简单删掉 `display:none`，而是针对移动端的**实际内容布局**重新设计一套安全区参数——手机端内容列本身就横跨了近乎全部视口宽度（只留很小的左右内边距），所以把水平安全区直接设为 `100%`（内容左右完全不透出水印），垂直方向沿用"上下露出水印带"的思路，同时缩小平铺图案尺寸、降低透明度以适配小屏幕。
- **注意事项**：遇到"某个装饰性效果在移动端不显示"时，第一步应该是去读一遍相关的 CSS 断点逻辑，搞清楚这是"代码遗漏"还是"当初为了避免固定像素值在窄屏下失效而特意关闭的取舍"；如果是后者，解决思路不是简单翻转 `display` 开关，而是要针对目标设备的真实布局比例，重新推导一套等效的参数，否则打开后大概率还是"看起来什么都没有"。

## 问题 24：本地代码改好了，但客户反馈"线上还是没变化"——要先确认改动有没有真的发布上去
- **问题描述**：修好了手机版 `code-pattern.svg` 水印不显示的问题（本地 headless 截图已验证效果正常），客户随后反馈"还是不会显示"，一度需要重新怀疑是不是 CSS 逻辑本身还有别的问题。
- **排查方法**：不要只在本地反复检查代码，而是直接用 `Invoke-WebRequest` 抓取线上真实域名（`https://bosmy.tech/styles.css`）的文件内容，搜索本次新增的关键代码片段（如 `max-width: 767px`）是否存在。结果发现线上文件里完全没有这次的改动，`hero-code-field` 相关规则数量和改动前一模一样——说明本地文件的改动从未同步到线上。
- **原因**：这个项目**没有连接 Git 仓库**（项目目录下没有 `.git`），线上部署是通过"手动打开 GitHub 网页、上传/编辑文件"完成的（和早前"图片丢失"那次排查确认的部署方式一致）。这种部署方式下，本地改完代码只是改了"草稿"，如果改完之后忘记再手动上传一次覆盖线上文件，线上网站看到的永远还是旧版本，客户端浏览器也会缓存旧文件，进一步掩盖"其实没发布"这个事实。
- **解决方案**：改完代码后，先用同样的方法（抓取线上文件、搜索关键片段）验证一遍"改动到底有没有生效"，而不是想当然地认为"我改完了、客户应该就能看到了"；确认没生效后，指导客户用 GitHub 网页的 "Edit this file" 或 "Upload files" 功能重新上传对应文件覆盖旧版本，并提醒发布后清浏览器缓存/强制刷新再验证。
- **注意事项**：对于"没有连接 Git 仓库、走手动网页上传部署"的项目，每次改完代码交付给客户之前，都应该主动提醒"这次改动需要重新上传到 GitHub 才会生效"，并且在客户反馈"没看到效果"时，第一时间去抓取线上真实文件核对，而不是先假设代码逻辑有问题重新排查一遍。

## 问题 25：想让"平铺背景图里的文字"动起来时，先分清它是"图片"还是"DOM 文字"，会决定能做到什么程度的动态效果
- **问题描述**：客户希望首屏 `background-image: url(code-pattern.svg)` 铺出来的代码水印呈现"漂浮"的动态效果，如果不假思索直接在 `.hero-code-field` 上加 `animation`，只能整体挪动/淡入淡出这一整张背景图，没办法让"某一行代码"和"另一行代码"用不同的节奏各自漂浮——因为浏览器把 `url()` 引用的 SVG 当成一张不可拆分的位图/矢量图片来渲染，CSS 无法穿透进去操纵图片内部的某个 `<text>` 节点。
- **解决方案**：如果目标动态效果需要"图内的某几个元素各自独立地动起来"，就不能再用 `background-image` 引用外部 SVG 文件这种方式，必须把这些内容改造成页面自己的 DOM 节点（内联 `<svg>` 或者像本项目一样直接用 `<pre>+<span>` 写 HTML 文字），这样每一个节点才能各自绑定独立的 `animation-name`/`animation-delay`/`animation-duration`。代价是失去了"一张图 `background-repeat` 无限铺满任意宽度"的省事写法，需要手动摆放固定数量的元素、并对不同断点分别设计布局。
- **注意事项**：接到"让某个背景图案/水印动起来"的需求时，第一步先确认这个图案当前是通过 `background-image`/`<img>`（图片、CSS 摸不到内部结构）还是内联 `<svg>`/普通 DOM 元素（CSS 可以摸到内部结构）实现的，这直接决定了"简单加个 `animation` 就能做到"还是"要先把实现方式换成 DOM 元素才能做到"，避免在错误的实现方式上反复调 `animation` 参数却怎么都做不出想要的逐个独立效果。

## 问题 26：给"只设置 `right`（或只设置 `left`）"的绝对定位元素做响应式验证时，只看宽分辨率会漏掉常见桌面宽度下的裁切问题
- **问题描述**：给 Hero 背景新增的多条独立漂浮代码行，用 `right: calc(50% + 内容区半宽 + 额外间距)` 定位（不设置 `left`，让文字内容向左自然展开），在 1440px 宽度截图验证时看起来完全正常；但换到更常见的笔记本宽度（1366px/1280px）时，个别文本较长的行会因为可用边距变窄，导致文字左边缘贴近甚至越过视口左边缘，出现裁切。
- **原因**：这种"只锚定一侧、内容向另一侧自然展开"的定位方式，元素实际占用的空间 = 锚点位置 ± 文本自身宽度，而不是一个固定尺寸的盒子；可用的安全边距是随视口宽度线性变化的，越窄的分辨率边距越小，如果只用一个很宽的分辨率（如 1440/1920）去验证，很容易得出"没问题"的错误结论。
- **解决方案**：验证这类"锚定一侧 + 内容自适应展开"的定位效果时，除了常见的桌面宽分辨率，一定要额外验证中间档位的常见笔记本宽度（1280/1366），并针对文本长度差异较大的元素，给"额外间距"值做保守收紧（不要为了追求"错落感"给太大的数值），保证在这些中间宽度下依然有余量。
- **注意事项**：以后凡是用"只设置一侧方位属性"的绝对定位去摆放长度不固定的文本内容，默认就要把"中间常见分辨率下的边距是否足够"纳入必测清单，而不是等宽屏验证通过就直接收工。

## 问题 27：客户要求"动效再大胆加大"时，优先设计成"结构上不可能违规"，而不是"调大数值再逐个截图验证"
- **问题描述**：给 Hero 漂浮代码行加大摆动幅度时，如果只是简单地把原来双向摆动（`translate3d` 的 X/Y 既可能是正值也可能是负值）的数值等比例放大，随着幅度越来越大，"会不会因为摆得太猛而摆进中间 Logo 安全区"这件事就越来越难通过肉眼/截图去逐一验证，而且客户后续大概率还会继续要求"再大胆一点"，每次加大都要重新验证一遍效率很低。
- **解决方案**：把"双向摆动"改成"单向摆动"——左侧的水印只允许摆动方向的水平分量为负（只往更左边/更远离中心的方向摆），右侧的水印只允许水平分量为正（只往更右边摆），这样无论幅度数值调多大，水平方向上都只会让元素"更加远离"安全区，绝不会"更靠近"安全区，从数学结构上就排除了"摆进中间区域"的可能性，不需要再逐个分辨率截图验证。垂直方向因为本来就不影响水平安全边界，可以完全放心地大幅加大。
- **注意事项**：以后遇到"效果要更强烈/更大胆，但同时有一条不能违反的边界"这种需求时，第一反应应该是先想"能不能把方向约束设计进动画本身"，而不是"选一个看起来安全的数值，靠反复截图去赌它在各种情况下都不会出问题"——前者一劳永逸，后者每次加量都要重新验证，且验证本身（尤其是动态效果）很难覆盖所有情况。

## 问题 28："只锚定一侧"的文本贴边裁切，如果文本本身长度已经超过可用边距，调偏移量数值治标不治本
- **问题描述**：给 Hero 漂浮代码水印新增内容时，两条超过 30 字符的长文案（`UPDATE inventory SET qty = qty - 1`、`Billing → Ledger → Reconciliation`）在 1366px 常见笔记本宽度下截图验证，发现贴视口边缘裁切明显；先尝试把 `Lesson.md` 问题 26 的方案再用一次——调小锚点的"额外间距"数值——裁切情况只是略微缓解，没有根治。
- **原因**：`right/left: calc(安全区边缘 + N)` 这种定位方式，box 的位置 = 安全区边缘 - N（另一侧由内容自身宽度撑开）；N 只能决定"文本整体往哪个方向挪一点"，改变不了"文本本身有多宽"。当文本自身宽度已经逼近甚至超过该视口宽度下的可用安全边距时（比如 13px 等宽字体、30+ 字符的文本，宽度轻松超过 250px），不管 N 取多小，文本的另一端都必然会伸出可用边距之外——这已经是"内容装不下容器"的问题，不是"定位数值没调对"的问题。
- **解决方案**：遇到这种情况，先估算"这段文本在目标最小验证宽度下的可用边距里装不装得下"（等宽字体可以用"字符数 × 单字符像素宽度"快速估算），如果明显装不下，直接把文案改短，而不是继续在偏移量数值上反复试探；本次把两条文案分别精简为 `inventory.qty -= 1`、`Billing → Ledger` 后一次性解决，不需要再调任何定位参数。
- **注意事项**：以后往这类"锚定一侧、按内容自适应展开"的装饰性文本队列里新增内容时，应该提前给文案长度定一个上限（本项目实测 13px 等宽字体下，24 个字符以内在主流笔记本宽度下比较安全），超过这个上限的新增文案要先精简，而不是加完之后再反复调偏移量去补救。

## 问题 29：给每个元素"设置了不同的数值"，不代表视觉上真的能看出"随机/分散"——要按视口尺度衡量差异
- **问题描述**：给 24 行漂浮代码水印的横向位置各自设置了不同的偏移量（2~28px 不等），本以为已经足够"各不相同"，但客户截图反馈看起来像是贴边排成了一条直线，像排队。
- **原因**：2px 和 28px 之间的差异只有 26px，放在 1300~1400px 宽的视口里占比不到 2%，人眼在这种尺度下根本分辨不出这点差异，所有行的贴边一侧看起来就像对齐在同一条竖线上；同时垂直方向的位置又是严格按固定百分比等差排列（如每隔 8%），本质上是一个规整网格，只是网格间距不均匀被误以为是"随机"。
- **解决方案**：设计"看起来分散/随机"的位置分布时，数值差异要按照实际渲染尺度（视口宽度、容器高度）去评估，确保关键维度上的极差达到能被肉眼分辨的量级（本次把横向偏移的范围从 26px 拉大到 76px 左右），同时避免用固定步长的等差数列摆位置，改成手动挑选疏密不均的散点数值。
- **注意事项**：以后凡是要做"分散/随机/自然"的视觉效果，不要满足于"每个数值都不完全相同"这个最低标准，而是要具体计算"这些数值之间的差异，相对于它们所在的容器尺寸，是否大到肉眼能感知"，同时要检查排布规则本身是不是暗藏了一个规整的等差网格。

## 问题 30：验证多个独立漂浮元素的效果时，要分清"静止布局排列过密"和"运动中偶尔交叉"是两回事，不要把后者当 bug 修
- **问题描述**：给漂浮代码水印加大横向摆动幅度后，headless 截图里发现两行文字临时叠在了一起、颜色和字符交错难以辨认，第一反应是当成布局错误去排查。
- **排查方法**：先检查这两行的**静止基础位置**（不含动画位移的 `top`/`left`/`right` 数值）之间的间距是否本来就太小——如果本来就贴得很近，是真的布局问题，需要重新分配位置；如果基础位置间距是充足的（比如 6% 以上），那么截图里看到的"叠在一起"只是因为每一行有自己独立的 `animation-delay`，恰好在截图这一帧，两个独立漂浮的元素的动画位移让它们的实际渲染位置暂时靠得很近——这是"多个独立运动的物体偶尔路径交叉"的正常现象，不是排布错误。
- **解决方案**：只修"静止位置本身间距不够"这一类真问题（本次把左右两侧各 12 行的最小间距统一调整到 6% 以上）；"运动中偶尔交叉"如果本来就是需求要的效果（比如客户明确要求"穿插"），就不需要、也不应该消除它——消除的代价通常是缩小摆动幅度或增大静止间距，会直接违背"更散、更明显地动起来"的需求。
- **注意事项**：以后遇到"多个独立动画元素的截图里出现重叠"，先问自己"这是它们本来站的位置就太近，还是只是恰好在这一帧运动到了一起"，两种情况的修复方向完全相反，判断错了会越改越偏离需求。

## 问题 31：`msedge --headless --virtual-time-budget=N` 不会推进 CSS `@keyframes` 动画的播放时钟，不能用它截取动画不同时间点的画面
- **问题描述**：想验证 CSS 漂浮动画在不同播放进度下的画面，尝试用两个不同的 `--virtual-time-budget` 取值（如 1500 和 4000）分别截图，指望能看到动画播放到不同程度的效果，结果两张截图像素级完全一致，都停在动画的起始状态。
- **原因**：`--virtual-time-budget` 影响的是 Chromium 的虚拟时钟，主要用于让依赖 JS 定时器（`setTimeout`/`setInterval`）、网络请求等待的页面"快进"到某个状态再截图；CSS `@keyframes` 动画走的是渲染合成器自己的时钟，不受这个虚拟时钟驱动，所以调大这个参数并不会让 CSS 动画"播放"得更久。
- **解决方案**：如果需要通过截图间接观察 CSS 动画的效果，不要依赖 `--virtual-time-budget`，改用默认方式截图（不加这个参数），此时页面从真实加载到截图之间会经过一小段真实的挂钟时间，加上每个元素各自不同的负值 `animation-delay`（让不同元素在页面刚加载时就已经处于各自动画周期的不同相位），足以在单张截图里观察到"不同元素运动到了不同位置"这种效果，间接确认动画正在按预期独立运转。真正需要"跳到动画播放到第 N 秒"的精确画面时，headless `--screenshot` 这条路径做不到，只能用真实浏览器手动打开肉眼观察，或者用 Puppeteer/Playwright 之类支持 `page.evaluate` 手动改写 `animation-delay`/暂停动画的工具。
- **注意事项**：以后凡是想用 headless 截图验证 CSS 动画效果，默认预期是"只能看到某个不可控的随机相位快照"，不要浪费时间去调 `--virtual-time-budget` 试图控制动画进度到某个精确点。

## 问题 32：给已有的一批装饰性元素"追加新一批"时，只在新批次内部核对数值是不够的，必须和已有批次合并成一个整体重新核算
- **问题描述**：给已有 24 行漂浮水印再追加 12 行时，新 12 行内部各自数值都不重复、看起来也够分散，但截图发现好几处新旧行的 `top%` 几乎完全相同（比如都在 88% 附近），静止状态下就叠在了一起。
- **原因**：设计新批次数值时，参考的是"这一批内部要分散"，没有把已有批次的数值也拉出来一起比较，两批各自看都合理，合并后却在同一个坐标系里撞车。
- **解决方案**：任何"追加式"扩充（不管是加数量、加变体），只要新旧元素共享同一个定位空间，就要把新旧全部数值当成一个集合重新统一核算最小间距/差异化，而不是孤立地只检查新增部分。
- **注意事项**：以后每次给同一容器里的重复性装饰元素"扩容"，第一步先列出全部（旧+新）元素的定位数值表，再检查这张完整表格里有没有过近/重复的值，不要只看新增的那几个。

## 问题 33：不确定某块区域"实际可用空间有多大"时，别凭直觉估算再调参数试错，用临时高亮 + 冻结动画直接量出来
- **问题描述**：往手机端"内容上方留白区域"塞入新的水印行时，凭直觉估算这块空间大约有 14% 的 hero 高度可用，结果新行几乎贴到了眉标签（`.eyebrow`）上；这类布局的可用空间还会随视口宽度变化（越窄的视口文字越容易换行、内容越高，留白反而越少）。
- **解决方案**：给目标元素（本例是 `.eyebrow`）临时加 `outline` 高亮，给待验证的水印行临时加 `background` 高亮并加 `animation: none !important` 冻结在静止基础位置，截图后就能一眼看出真实边界在哪，量出安全范围后再删掉这些临时调试样式。这比"猜一个数值 → 截图 → 不对 → 再猜一个"的试错循环快得多，也更准确。
- **注意事项**：以后凡是"这块空间到底有多宽/多高"说不准的情况（尤其是 flex 居中、内容高度随文字换行变化的布局），第一反应就是用临时高亮 + 冻结动画的方式截图实测，而不是靠公式心算。

## 问题 34：设计"看起来均匀分散"的散点分布时，光顾着让间隔"不规则"还不够，还要限制"最大间隔"这个上限
- **问题描述**：把 18 个元素的位置间隔设计成 3%~8% 的不规则数值，本意是避免"整齐网格"的观感，结果客户反馈截图里两侧仍有明显的空白区块。
- **原因**：3%~8% 的间隔本身确实"不规则"，但在近千像素高的容器里，8% 对应着 70~80 像素的空白，而单行文字只占 18~20 像素，中间几十像素的空隙足以被肉眼看成一整条空白带；"不规则"只解决了"看起来像网格"的问题，没有解决"局部密度不够"的问题。
- **解决方案**：把间隔的取值范围收窄到 4%~6%（仍保留抖动、不是严格等差），用"控制最大间隔上限"来保证任意位置的局部密度都够，而不是单纯追求数值之间的不规则性。
- **注意事项**：以后设计散点分布，除了检查"数值是否重复/是否等差"，还要单独检查"排序后相邻两个数值的最大间隔，换算成实际像素后是否会形成肉眼可见的空白"，这是两个独立的检查项，缺一不可。

## 问题 35：加大已有动画的摆动幅度前，要重新核算"深度定位 + 摆动幅度"的总和会不会超出安全边界，而不能只加大幅度、沿用旧的定位数值
- **问题描述**：把漂浮水印的横向摆动峰值从 40~44px 加大到 58~62px 之后，用真实动画截图看起来没问题，但后来用"冻结峰值位移"的方式专门截图复查，发现好几行文字在摆动到最远处时会被视口边缘裁切掉开头几个字符——而这些行的定位数值（偏移量）是在旧的、较小摆动幅度下设计并验证过"安全"的。
- **原因**：每一行文字能不能安全摆到最远处，取决于"基础偏移量 + 摆动幅度 + 文字宽度"这三者的和是否超过视口边界，之前的偏移量分配是按旧幅度校准的，加大幅度相当于让这个总和变大，原来刚好够用的安全余量就不够了；仅凭"真实动画截图看起来没问题"来验证是不可靠的，因为每一行何时摆到自己的最远处取决于各自的 `animation-delay`，随手截一张图很可能所有行都不在最远处。
- **解决方案**：① 用临时把关键帧改写成只有一帧、直接定格在峰值 `transform` 的方式截图，一次性看到全部同类动画元素在最极端情况下的样子，而不是靠随机相位的真实动画截图去"撞运气"抓裁切；② 发现裁切后，优先把文案统一收紧到一个安全长度以内（而不是给每一行精细调参），让同一套"文字越短、偏移量上限越高"的简单规则能一次性覆盖所有行。
- **注意事项**：以后凡是"调大一个已经和其他数值（定位、文字长度）绑定校验过的动画参数"，都要意识到这会打破原来的校验结果，必须重新校验，不能想当然地认为"以前验证过安全，现在加大参数应该也还好"。

## 问题 36：只在一个基准宽度下验证过"安全"的固定 px 动画参数，可以换成按该基准换算的 vw 表达式，让效果自动适配任意视口宽度
- **问题描述**：横向漂浮幅度和偏移量此前都是按 1366px 这一个基准宽度手工调出来的固定 px 数值——1366px 下没问题，但更宽的屏幕（1920/2560px）明明有更多可用边距却没利用上，更窄的屏幕又需要重新手算一遍才能确认安全。
- **原因**：固定 px 数值不会随视口宽度变化，而实际的"安全区外可用空间"是随视口宽度线性变化的；用一个基准宽度调出来的数值，本质上只对那一个宽度是"刚好合适"，其他宽度要么浪费余量、要么不够用。
- **解决方案**：把水平方向（会导致裁切风险的那个轴）的动画数值改写成 `min(CAPpx, Xvw)`（正向偏移）或 `max(-CAPpx, -Xvw)`（负向偏移）——`Xvw` 按原基准宽度换算得出（换算方式：原 px 值 ÷ 基准宽度 × 100），保证在基准宽度下数值不变；`CAP` 用固定 px 封顶，避免在超宽屏上无限变大。这种"单侧限制"用 CSS `min()`/`max()` 就够，不需要三参数的 `clamp()`。与视口边缘裁切无关的轴（比如纵向位移）不需要跟着改，避免无谓扩大改动范围。
- **注意事项**：改完之后不能想当然认为"vw 会自动处理好一切"，仍然要用"冻结峰值位移"的方式，把原来验证过的基准宽度、以及新覆盖到的宽和窄两端，各截一张图复验一遍——尤其要留意断点边界（比如 `min-width: 1024px` 刚生效的 1024px 本身），因为断点两侧如果内容宽度差异很大，那个边界值可能是整个响应区间里最危险的一点，光验证常见的桌面分辨率容易漏掉它。

## 问题 37：用一次性截图验证"CSS 动画会不会在某个宽度下裁切"不可靠，`animation-delay` 决定的相位会和无头浏览器的启动耗时抖动混在一起
- **问题描述**：把断点从 1024px 试着改到 1200px 后，用"真实动画 + `--screenshot` 截图"在 1200px 复验，同一个宽度反复跑，结果时好时坏；相邻的 1250px、1300px 两个宽度，"越宽应该越安全"的直觉也被打破——1250px 反而比 1300px 裁切更多行。
- **原因**：页面里每一行水印的动画相位（当前处于摆动周期的哪个位置）由 `animation-delay` 结合"页面从开始渲染到截图那一刻经过了多久"共同决定；而用无头浏览器每次单独起一个新进程、加载页面、再截图，从进程启动到真正按下"截图"这个动作之间的真实耗时并不固定，会有几百毫秒到几秒的随机抖动（取决于系统当时的调度情况）。这意味着每次截图实际捕捉到的，是各行水印在自己周期里随机不同的一个瞬间相位——这和真正要验证的变量（视口宽度）搅在了一起，导致"同一个宽度测两次结果不一样""更宽的尺寸反而看起来更差"这类违反直觉的现象。
- **解决方案**：不要用"一次性截图"去验证这类和动画状态相关的问题。改用 Node 脚本通过 Chrome DevTools Protocol（CDP）连上同一个浏览器实例：① 先注入一段样式，把全部相关 `@keyframes` 强制改写成只有一帧、定格在各自的峰值 `transform`（彻底去掉"时间"这个变量，动画状态变成确定性的）；② 用 `Emulation.setDeviceMetricsOverride` 在同一个已经加载好的页面里连续切换视口宽度（不用重新起进程、不用重新加载页面，规避每次启动的随机抖动）；③ 每次切换宽度后，直接用 `Runtime.evaluate` 读取真实 `getBoundingClientRect()`，用代码判断是否越界，而不是靠肉眼看压缩过的截图小字。这样测出来的结果，宽度之间只有"宽度"一个变量在变化，结论才可信。
- **注意事项**：以后凡是"用截图判断 CSS 动画在某个状态/尺寸下对不对"，都要先想清楚这次截图捕捉到的到底是动画的哪个瞬间、这个瞬间是不是确定性的——如果不是（比如依赖 `animation-delay` + 真实耗时），要么把动画冻结成确定性状态再截图，要么直接放弃截图，改用代码读取真实布局数据（`getBoundingClientRect`、`getComputedStyle` 等）来做判断，后者对于"差几个像素"这种精细边界问题尤其重要，肉眼读小字截图很容易看错或看漏。

## 问题 38："不裁切"和"用满可用空间"是两个独立的检查项，只按固定基准换算的 vw 比例只能保证前者
- **问题描述**：上一轮把水印偏移量从固定 px 改成"按 1366px 换算的 vw 比例 + px 上限"之后，用 CDP 验证过全部目标宽度都不裁切；但客户随后截图反馈，宽屏下水印离真实的视口边缘还有明显一截留白没填上，越宽的屏幕留白越夸张。
- **原因**：换算出来的 vw 系数（原始 px 值 ÷ 1366 × 100，约在 2%~4% 之间）是一个几乎不随宽度变化的"扁平比例"；而真正决定"还有多少空间可以用"的可用空间（margin = 视口宽度/2 − 安全区半宽）却是按接近 50% 的斜率随宽度线性增长的。两者增长速度相差十几倍，宽度越往上，供给（vw 系数算出来的偏移量）远远追不上需求（可用空间），差距只会越拉越大——这类问题不会在"是否越界裁切"的检查里暴露出来（因为供给增长得慢，天然更安全，不会裁切），必须专门去量"实际用掉了可用空间的百分之多少"才能发现。
- **解决方案**：把偏移量公式从"固定比例的 vw"改成直接以"可用空间本身"为基准的公式：`FRACTION × max(0px, 可用空间表达式 − 该元素固定占用的宽度 − 缓冲)`，其中"可用空间表达式"（比如 `50% − 安全区半宽px`）本身就是一个随视口宽度线性变化的量，让偏移量天然跟着可用空间等比例伸缩，而不是伸缩得比它慢。用 `FRACTION`（0~1 的系数，取自原本设计里每个元素的相对深度/重要性排序）区分"该更靠边"和"该更靠中间"的元素，保留原有的错落层次；`max(0px, …)` 防止在最窄宽度下公式算出负值而破坏原有的安全边界。配合 CDP 精确测量每个元素固定占用的真实宽度（而不是估算），可以让这个公式的安全边界算得很准，不需要再靠经验值预留很宽的冗余空间。
- **注意事项**：以后验证"一个元素的位置/尺寸是否随容器/视口自适应"，不能只检查"有没有超出边界"这一个指标，还要专门加一个"实际用掉了可用空间的多少比例"或"离边界还剩多少像素"的量化指标，两者是独立的检查维度——前者只能防止"太过分"，后者才能防止"不够用力"。

## 问题 39：图片"展示尺寸"和"实际分辨率"不匹配，是很容易被忽略的性能问题，且用索引色（palette）压缩对简单图形几乎无损
- **问题描述**：`bos-mark-transparent.png` / `bos-mark-white.png` 两张 logo 实际分辨率是 828×569，但页面上最大只用到 168px 宽（Hero 处），导航栏和页脚用得更小（62px / 22px）——这类"图片分辨率远超实际展示需要"的问题不会在视觉上表现出任何异常（图片显示依然清晰、正常），只会安静地拖慢加载速度，很容易在开发过程中被忽略。
- **原因**：只要 CSS 里给了明确的展示宽度（如 `width: clamp(120px, 16vw, 168px)`），浏览器会把原图缩小显示，视觉上完全看不出"其实传输了一张几倍大的图"，必须主动去对比"图片实际分辨率"和"页面里最大的展示尺寸"才能发现。
- **解决方案**：① 找到该图片在全站所有引用位置里"展示尺寸最大"的那一处，乘以一个视网膜屏倍数（通常 2~3 倍）作为目标分辨率，用 `sharp` 的 `resize({width})` 缩小；② 对于本身颜色种类很少的图形（这次是黑/白+描边灰阶的字母 Logo），额外加上 `png({palette: true})` 做索引色量化，比单纯调高 `compressionLevel` 的无损压缩幅度大得多（本例从 78KB 降到 29KB，而只调 `compressionLevel` 只能降到 56KB）；③ 压缩后一定要用图片查看工具肉眼对比前后效果，索引色量化对"颜色种类本来就少"的图形几乎无损，但对渐变、照片类图片可能出现明显色带，不能不看效果就直接用。
- **注意事项**：审计一个项目"图片是否需要优化"时，不能只看文件大小是否"看起来很大"，要具体去核对"实际分辨率 vs 页面里最大展示尺寸"这一组数字；调整完图片之后，同时给对应的 `<img>` 标签补上和新分辨率一致的 `width`/`height` 属性，让浏览器在图片加载完成前就能按正确宽高比预留版面空间，避免布局抖动（CLS）。

## 问题 40：项目没有构建步骤时，任何留在项目目录内的文件（包括备份、原图、文档）理论上都会被原样部署上线
- **问题描述**：优化 logo 图片时，第一反应是把压缩前的全尺寸原图备份成 `xxx-original.png` 留在同一个 `assets/` 目录里，后来意识到这样不合适。
- **原因**：本项目 `main.js` 开头就写明"Vanilla JS only. No frameworks, no build step."——没有构建/打包流程，意味着部署时很可能是把整个项目目录原样上传到静态托管。在这种前提下，"项目目录内的某个子文件夹"和"公开可访问的 URL 路径"是等价的，不存在"看起来是内部文件就不会被访问到"这种安全边界；同理，项目根目录下的 `README.md`/`Progress.md`/`Lesson.md`/`Project-status.md` 等工作日志文件、以及 `index - 副本.html` 这类备份文件，如果部署时整目录原样上传，也都会变成公开可访问的 URL。
- **解决方案**：任何不打算公开的文件（全尺寸原图备份、临时调试脚本、内部文档等），一律放到项目目录**之外**（比如项目文件夹的同级目录），而不是项目目录内部的某个专门文件夹。
- **注意事项**：以后接手"无构建步骤、整目录直接部署"的项目时，第一次涉及"要不要留一份备份/原始文件"的场景，都要先确认清楚部署方式，默认按"项目目录内的任何东西都会公开"这个更保守的假设处理；如果客户之后决定引入构建步骤或换成有 `.gitignore`/部署白名单的流程，再放宽这条限制。

## 问题 41：怀疑"某个文件可能被公开部署了"时，要用真实 HTTP 请求核实，而不是只靠本地文件结构推测；也不要只信第一次工具返回的结果
- **问题描述**：本地项目根目录里有 `README.md`/`Progress.md`/`Project-status.md`/`Lesson.md`（工作日志）、若干 `xxx - 副本.xxx` 备份文件、以及一个 `.pptx` 文案整理文件。凭"项目没有构建步骤，整目录可能原样部署"这个此前的经验，需要判断这些文件里到底哪些真的暴露在线上（`bosmy.tech`）、哪些没有。
- **原因**：光靠本地文件是否存在无法判断线上真实情况——实际部署可能来自另一个 git 仓库/发布流程，本地目录只是工作副本，两者不一定完全同步；必须用真实请求逐个核对。另外，第一次用网页抓取工具查 `sitemap.xml` 时返回了"500 Internal Server Error"，一度以为线上 sitemap 坏了，但换用 `curl.exe` 直接发请求后返回的是正常的 `200 OK` 和完整内容——说明第一次的"500"是抓取工具自身（可能是它内部的代理/解析层，对 `application/xml` 内容类型处理有问题）的问题，不是网站真的出错，如果不用第二种方式复核，会得出一个错误的"生产环境有 bug"结论并可能误导客户去排查一个不存在的问题。
- **解决方案**：① 对每一个"怀疑被部署"的文件，用 `curl.exe -s -o NUL -w "%{http_code}"` 直接请求真实 URL 拿到确定的 HTTP 状态码逐一核实，文件名含中文/空格时用 `[System.Uri]::EscapeDataString()` 正确编码，不能手写百分号转义（容易转错）；② 如果某个工具给出的结果和预期严重不符（比如"静态 XML 文件返回 500"），先换一种独立的方式（比如换一个请求工具/方式）复核一遍，确认是真实问题还是工具本身的误报，再据此下结论或采取行动；③ 核实结果：`README.md`/`Progress.md`/`Project-status.md`/`Lesson.md` 四个工作日志文件确认被公开部署（HTTP 200，能读到真实内容），`sitemap.xml` 其实一切正常（是抓取工具误报），所有 `- 副本.*` 备份文件与 `.pptx` 文件均未被部署（HTTP 404）。
- **注意事项**：以后凡是"这个文件/接口是不是真的对外暴露/是不是真的有问题"这类判断，只要能发真实网络请求验证，就不要停留在推测或单一工具的一次性结果上；发现异常结果时，先怀疑"是不是测量方式本身的问题"，用另一种独立方式交叉验证一次，才能确定后续该做什么（该修代码，还是该忽略）。

## 问题 51：顶栏「Services」改名 Home 时，链接应指向首页而非 #services

## 问题 52：UTF-8 多字节标点损坏会表现为「黑菱形/问号/??」
- **问题描述**：首页与能力深页出现 ``、语言切换变成 `??`、箭头变成 `?`。
- **原因**：`—`/`→`/`↓`/`中文` 在错误保存或脚本重写时丢失字节，变成 U+FFFD 或 ASCII `?`。
- **解决方案**：批量把 U+FFFD 还原为 —；语言链还原为「中文」；`?` 箭头按上下文还原为 →/↓；再用码点扫描确认无控制字符。
- **注意事项**：PowerShell 控制台可能把合法 Unicode 显示成乱码，必须以文件码点/浏览器为准；Windows 下改 HTML 应用 UTF-8 无 BOM 写入。

## 问题 53：顶栏改成多页路由后，旧 hash scroll-spy 会失效
- **问题描述**：交互审计发现 `a[href^="#"]` spy 几乎无目标。
- **原因**：导航已是 `/process/`、`/contact/` 等绝对路径。
- **解决方案**：按 pathname 高亮；首页额外用 `#process` 区块位置切换 Home/Process 的 `is-active`；移动菜单加 `body.nav-open` 与 Tab 陷阱。
- **注意事项**：FAQ 用 `details/summary` 保可索引，JS 只做「同时只开一项」。

## 问题 54：正式专业字体要同时照顾拉丁大小写对比与中文回退
- **问题描述**：用户要求字体更正式、专业、大小写分明。
- **原因**：原 Fraunces 偏编辑/斜体气质，Manrope 偏产品圆润，正式感不足。
- **解决方案**：Source Serif 4（标题）+ Source Sans 3（正文）+ IBM Plex Mono（全大写标签）；zh 加 Noto Serif/Sans SC；Hero 改正体。
- **注意事项**：避免 Inter/Roboto；全大写用字距与字重区分，正文保持句首大小写。

## 问题 55：删除某一语种时要同步入口、hreflang、sitemap 与物理目录
- **问题描述**：用户要求删除马来语。

- **解决方案**：批量去掉 BM 链与 ms 元数据；删除 `ms/`；sitemap 去掉 ms 条目与 alternate；`main.js` 首页仅识别 `/` 与 `/zh`。
- **注意事项**：部署后旧 `/ms/` 会被 404，可在托管层做 301 到英文首页（可选）。

## 问题 56：补全中文深页时，语言切换必须指到「对应页」而非一律回首页
- **问题描述**：用户要求补全各页面中文。
- **原因**：原先只有 `/zh/` 首页，深页点「中文」会丢上下文。
- **解决方案**：建立 `/zh/*` 镜像；EN↔ZH 语言切换与 hreflang 成对；sitemap 收录双语 URL。
- **注意事项**：写 head 的 `rel="alternate"` 时不要用「是否含 hreflang=zh-Hans」判断（切换链也会命中）。

## 问题 57：导出全站文案做关键词检索时，要排除装饰层
- **问题描述**：用户需要 MD 列出各页文字以便搜关键词。

- **注意事项**：清单放 `md/`（内部文档）；文案大改后需重新生成。

## 问题 58：全站文案重写必须严格贴清单，禁止自创

- **注意事项**：清单未写的 hero 文案只用清单内已有字段（能力名、痛点、摘要等）填充结构位，勿另写营销句。

## 问题 59：中文站重写同样只贴清单，能力页 H1 用能力名+痛点填结构位
- **问题描述**：中文站需按清单重写，禁止自创文案。

- **注意事项**：路径不改；导航标签不变；kuching 页脚与正文可写古晋，其它页脚仅「服务马来西亚各地企业」。

## 问题 60：Service Areas 正文标题勿与 Hero 同文双现

## 问题 61：FAQ 增删必须同步 JSON-LD 与双语
- **问题描述**：FAQ 页可见问答与 FAQPage 结构化数据、英中版本易脱节。

## 问题 62：用户给定中文首页改写时，英文同步结构勿留空痛点区

## 问题 63：FAQ Hero 简化时去掉与 H1 重复的 eyebrow
- **问题描述**：Hero 主标题已是「常见问题：」时再保留 eyebrow「常见问题」会重复。
- **解决方案**：只保留 H1 + page-lead；meta description 跟短描述对齐。
- **注意事项**：浏览器标题 `<title>` 可仍保留较长 SEO 句，与可见 H1 分开。

## 问题 64：中文首页锁定标语按客户要求可不带句号
- **问题描述**：客户要求「我们通过数字化系统，简化复杂的商业运营」首页展示无句号。
- **解决方案**：只改 `zh/index.html` 可见 H1；内部清单历史文档可不强制回写。
- **注意事项**：与英文句末句号是否对齐，以客户当次指令为准。

## 问题 65：SEO 对比要区分「技术卫生」与「综合竞争强度」
- **问题描述**：小站标签齐全易被误判为 SEO 已强。
- **原因**：竞品靠内容厚度、案例/博客、本地信任与索引权威拉开差距。
- **解决方案**：分维评分（技术/内容/覆盖/信任/索引）；先修线上故障（如 sitemap 500）再堆内容。
- **注意事项**：无 Ahrefs/GSC 时结论应标明「公开信号判断」，避免伪精确。

## 问题 66：用户要求「拿本地作对比」时必须排除线上因素
- **问题描述**：混入线上 sitemap 500/旧部署会扭曲对本站源码 SEO 就绪度的判断。
- **解决方案**：本站只扫本地 HTML/sitemap/robots；竞品可用公开页；Canvas 明确口径。
- **注意事项**：中文页勿用空格分词当「词量」与英文硬比。

## 问题 67：能力问答页可挂在能力路径下的 /qa/
- **问题描述**：五项业务问答需独立页并从业务入口跳转。
- **解决方案**：`/capabilities/{slug}/qa/`（中文 `/zh/.../qa/`）；顶栏五业务标签直达；sitemap 成对收录。
- **注意事项**：一页多个 `.faq-list` 时，`initFaqAccordion` 必须 `querySelectorAll`；用户不要「业务下行进 FAQ」式入口，而要顶栏独立业务标签。

## 问题 68：顶栏多项 nowrap 时会叠到 Logo / 语言切换
- **问题描述**：强制单行后链接溢出，与品牌区、语言切换视觉重叠。
- **解决方案**：中间列 `minmax(0,1fr)` + `overflow:hidden`；品牌/操作区 `z-index` 与不透明底；长导航隐藏 wordmark；≤1400px 改汉堡。
- **注意事项**：不要给整个 `.nav` 设 `overflow:hidden`，否则会裁掉下拉菜单。

## 问题 69：PowerShell 下不要用 `curl` 做健康检查
- **问题描述**：Windows PowerShell 把 `curl` 映射为 `Invoke-WebRequest`，`-s`/`-o`/`-w` 会报错。
- **解决方案**：健康检查改用 `curl.exe`。
- **注意事项**：本地预览纯静态站用 `python -m http.server` 即可，无需 npm 构建。

## 问题 70：BOS 这类本地 B2B 小站，SEO 必备工具不要买 Ahrefs
- **问题描述**：做 SEO 容易被工具清单带偏，一上来订阅 Ahrefs/SEMrush，数据很多但本站当前缺的是收录反馈、转化追踪和古晋本地曝光。
- **解决方案**：只备 4 个免费工具——Google Search Console（已验证）、GA4、Google Business Profile、Google Keyword Planner。GSC 看收录/查询词，GA4 看有没有人点 Contact，GBP 做古晋本地包，Keyword Planner 选词。
- **注意事项**：GSC 还没稳定出现查询量和点击之前，不要为了「看排名」去买付费外链/关键词工具；技术体检用 PageSpeed Insights 即可，不必单开账号。

## 问题 71：让 Cursor 协助做 SEO 时，没有必须下载的插件
- **问题描述**：用户问「要你协助做 SEO 必须下载什么插件」，容易联想到 WordPress 的 Yoast/Rank Math，或一堆 Chrome SEO 扩展。
- **解决方案**：本站是纯静态 HTML，SEO 全在源码（title/meta/schema/sitemap/内链），Cursor 直接改文件即可，不依赖任何 IDE/浏览器插件。Yoast、Rank Math 只适用于 WordPress，这里装了也没用。
- **注意事项**：需要真实搜索数据时，把 GSC/GA4 截图或导出贴进对话即可；Chrome 自带 Lighthouse（DevTools）够做技术体检，不必另装扩展。

## 问题 72：BOS 的 Google Business Profile 主类别应填 Software company，不要填 Website designer
- **问题描述**：GBP 没有「定制数字化系统 / Business Operating System」这类目；若把主类别设成 Website designer，会被推进古晋廉价建站搜索池，和品牌定位相反。
- **解决方案**：主类别只填 `Software company`；附加只加 `Computer consultant`（对应「先诊断再做系统」）。网站、CRM、自动化写在 Services，不当类别。不要填 Computer support、Internet marketing、Automation company（工业自动化）、Business management consultant。
- **注意事项**：类别必须从 Google 下拉列表选，不能手打自创；主类别决定本地包相关性，附加类别最多 1～2 个，不要为五项能力各填一类。

## 问题 73：站内 SEO 骨架已齐时，下一步不是再改标签，而是场外部署与收录
- **问题描述**：问「如何做我的 SEO」时，容易以为还要从 title/插件重新开始；本站多页、schema、sitemap、GSC 已落地，再堆标签边际收益很低。
- **解决方案**：本周只做三件场外：① 按 `md/GBP-NAP.md` 建 Google 商家资料；② 接入 GA4；③ 确认线上已部署最新站，并在 GSC 提交 `https://bosmy.tech/sitemap.xml`、对新 URL 请求编入索引。之后每周只看 GSC 搜索词/点击。
- **注意事项**：没有案例前不要硬写博客；不要买 Ahrefs。内容厚度是中期事，本周先把「能被 Google 找到、能看见数据」做完。
