### 2. 遇到的错误
1. PowerShell 默认代码页下中文目录名显示为 `??`，一度误判素材缺失。
2. Headless 截图 + `scroll-behavior: smooth` 组合导致锚点跳转截图截到动画播放中途的画面。
3. `subprocess.Popen` 启动的真实浏览器窗口不能稳定获得系统前台焦点，`ImageGrab` 全屏截图偶尔截到 IDE 窗口而非目标浏览器窗口。
4. 极窄 `--window-size`（390px）下 headless 截图出现"文字被裁切在画面边缘"的现象。
5. 紧凑循环中"启动浏览器 + 立即清理其 profile 目录"导致后续截图任务拿到空白页。

### 3. 错误的原因和解决方案
详见 `Lesson.md`，核心结论：
- 前 4 类问题均为**截图/调试工具本身的行为特性或环境限制**，均已通过隔离验证（如 iframe 容器测试）确认**不是网站代码本身的缺陷**。
- 已固化为可复用的调试方法：临时副本 + 强制去动画 + `virtual-time-budget` + 独立单次调用；GUI 自动化优先退回 headless。

- 用 `nth-child` 写死 `transition-delay` 做错落进场，会连带影响同一元素后续的 hover 过渡（共用了 `transform` 等属性），导致 hover 反馈短暂变卡顿。

### 2. 遇到的错误
- 最初把 `.eyebrow` 的 "// " 前缀实现为 `display:flex` + `::before`，在真实窄屏下会因 flex 子项默认 `min-width:auto` 无法换行，导致长文案（如 "MALAYSIA · CUSTOM-BUILT DIGITAL SYSTEMS"）右侧被截断。

### 3. 错误的原因和解决方案
- 第一个问题：改回最简单的写法——`.eyebrow` 保持普通块级排版，`::before { content: '// '; }` 作为行内内容前缀，不再引入 flex 布局，文本按正常规则换行；已通过移动端截图确认修复。
- 第二个问题：判断是环境侧的自动清理机制（非代码问题），采用"截图命令与读取图片之间不再插入其它 shell 调用"的方式规避竞态，重新截图后立即读取即可稳定拿到结果。

### 4. 下一步计划

## 导航栏固定补充记录（第六轮）

### 1. 完成了哪些功能
- 客户反馈导航栏"会因为页面移动而消失"，要求始终固定在顶部。
- 排查发现：`.nav` 本身一直是 `position: sticky; top: 0;`（本来就会一直贴顶），但第二轮交互优化时加过一个"向下滚动自动隐藏、向上滚动恢复"的效果（`main.js` 里 `initNavScrollBehaviour` 会在向下滚动超过首屏 60% 高度时给 `.nav` 加上 `is-hidden` 类，`styles.css` 里 `.nav.is-hidden { transform: translateY(-100%); }` 让它整个移出视口）——这个"智能隐藏"就是客户看到的"消失"。
- 按客户要求，彻底移除了这个隐藏行为：删除了 `main.js` 里 `updateVisibility` 函数及对 `is-hidden` 的所有判断逻辑，删除了 `styles.css` 里 `.nav.is-hidden` 规则，并同步清理了 `.nav` 上不再需要的 `transform` 过渡声明。现在导航栏只保留"滚动一段距离后出现描边+阴影"（`is-scrolled`）和"scroll-spy 高亮当前区块对应的导航项"两个效果，本身永远贴在视口顶部，不会再被移出屏幕。

### 2. 遇到的错误
- 无（属于按客户要求移除已有功能，非新增功能引入的 bug）。

### 3. 错误的原因和解决方案
- 根因：第二轮为了让交互"更丰富"主动加入的隐藏/显示效果，与本次客户的实际期望（导航栏应该一直可见、方便随时点击 Contact us）相冲突。已按客户最新反馈为准，移除该效果。

### 4. 下一步计划
- 无遗留问题；如果以后又想要"向下滚动缩小导航栏高度"之类更轻量的替代方案，可以再讨论，但当前版本导航栏是完全固定不隐藏的状态。

## 导航栏改为真正的 position: fixed（第九轮）

- 客户反馈"顶部 header 仍然会因为滚动而消失"，要求彻底把 header 固定在顶部、与下方内容隔绝：下方内容区域可以滚动，header 本身不参与滚动。
- 根因：`.nav` 此前用的是 `position: sticky; top: 0;`。Sticky 定位在有 `overflow-x: hidden`（`html`/`body` 上都设置了）这类会隐性影响 `overflow-y` 计算值的祖先元素时，不同浏览器/渲染场景下有已知的兼容性问题，可能导致贴顶效果不稳定、在某些滚动时机下失效，表现就是"滚动时消失"。
- 直接把 `.nav` 改成更明确、更不依赖祖先元素 `overflow` 状态的 `position: fixed; top:0; left:0; right:0;`——这样导航栏彻底脱离文档流，永远相对浏览器视口定位，不会再受任何滚动容器规则影响。
- 因为 `fixed` 元素会脱离正常文档流（不再占用自己的高度空间），给 `body` 补了一条 `padding-top: var(--nav-height);`，把原来"导航栏自己占位"让出来的空间用 `body` 的内边距补回来，保证 Hero 等后续内容不会被固定后的导航栏盖住、也不会出现多余空白。
- 桌面（1440px）、移动端（390px）截图确认：页面顶部布局与之前视觉一致，没有出现遮挡或空白；移动端汉堡菜单展开位置也依然正确（菜单的 `position:absolute` 是相对 `.nav` 定位的，`fixed` 同样能提供这个定位上下文，不受影响）。

### 2. 遇到的错误
- 无（这次是直接从"更宽松但有兼容性风险的 sticky"换成"更严格但更可靠的 fixed"，方案本身比较确定）。

### 3. 错误的原因和解决方案
- 详见上方"完成了哪些功能"，核心是 `position: sticky` 遇上 `overflow-x: hidden` 祖先时的已知兼容性弱点，改用 `position: fixed` 彻底绕开这个问题。

### 4. 下一步计划
- 无遗留问题。若后续要在导航栏下方新增依赖"正常文档流占位"的内容，需要留意导航栏已经是 `fixed`（不占文档流），不能再假设"导航栏后面紧跟着一段自然留白"，统一通过 `body` 的 `padding-top` 或各区块自己的 `padding`/`margin` 控制间距。

1. 用一个"人为设置得很高的 `--window-size` 高度（如 7500px）"来一次性截全页，结果 Hero 区块因为使用了 `min-height: calc(100vh - nav高度)`，`100vh` 被撑成和这个人为高度一样大，导致 Hero 内容被挤到"视觉上极靠下"的位置，页面顶部出现大片异常空白。
2. 用 `window.scrollTo(0, y)` 或 URL 锚点跳转（`#services` 等）配合 headless `--screenshot` 尝试截取页面中段/底部内容时，发现 `position: fixed` 的导航栏在截图里"跑"到了画面底部而不是始终贴顶，且页面主体内容也没有真正随之滚动显示，两种方式反复测试均如此。

2. 原因：这是本项目截图工具链里又一个新发现的 headless 特性（`--screenshot` 命令行截图 + `position:fixed` 元素 + 程序化滚动/锚点跳转的组合），滚动没有像真实浏览器交互那样正确反映到最终截图里，`fixed` 元素的定位计算也出现了明显错位——判断为截图工具本身的已知局限，而不是网站代码有 bug（页面本身在真实浏览器里滚动、导航栏贴顶都是长期验证过的正常行为，本轮也没有改动任何相关代码）。解决方案：改用"隐藏前置板块，让目标内容自然出现在页面顶部（scrollY 始终为 0）"的方式绕开程序化滚动，彻底规避这个坑。

- 用常规的"真实动画 + `--screenshot` 截图"方法在 1200px 复验时，同一宽度反复截图给出了自相矛盾的结果（有时干净、有时多行裁切），且相邻宽度（1250px 比 1300px 裁切更多）不符合"越宽越安全"的预期趋势。

### 3. 错误的原因和解决方案
- 原因：`animation-delay` 决定的动画相位，是相对"页面开始渲染"这个时间点计算的；而无头浏览器每次启动进程到真正截图之间的真实耗时并不固定（受系统调度影响，有几百毫秒到几秒的抖动），所以每次截图实际捕捉到的是各行水印在各自动画周期里随机不同的相位——这和"视口宽度是否安全"这个我们真正想验证的变量混在了一起，导致结果看起来毫无规律。
- 解决方案：改用 Node 脚本通过 Chrome DevTools Protocol 连接同一个浏览器实例，先注入样式把全部动画强制定格在各自关键帧的峰值 `transform`（去掉时间这个变量），再用 `Emulation.setDeviceMetricsOverride` 在同一个已加载好的页面里连续切换视口宽度并读取真实 `getBoundingClientRect()`——这样每个宽度的测量都是确定性的，互相之间只有"宽度"一个变量在变化。用这套方法复测后确认：1200px 仍有 8 行以 2~5 像素的微小差距裁切，1250px 是第一个完全干净的整数断点，因此最终把断点定在 1250px 而不是客户举例的 1200px。
- 额外用同样的方法验证了断点扩大后新覆盖到手机布局的 1024~1249px 这段宽度（之前从没有以"手机布局"的形态跑过这么宽的视口），在条带动画两种可能的摆动峰值下，从 360px 到 1249px 全部干净。

### 4. 下一步计划
- 无遗留问题。以后凡是要验证"某个视口宽度下 CSS 动画会不会裁切/出错"，优先用"CDP + 冻结峰值 + 读取真实 DOM 矩形"的方法，不要单纯依赖一次性截图，尤其是在需要精确到个位数像素级判断安全边界的场景下。

## 填满宽屏两侧水印留白，手机端摆动幅度同步适配（第三十三轮）

### 1. 完成了哪些功能
- 客户截图指出桌面版两侧真实视口边缘附近还有明显留白，要求填满，并要求同步适配手机端。
- 把 36 行侧边水印的偏移量公式从"按 1366px 换算的固定 vw 比例"改成"填满安全区到视口边缘之间剩余空间"的公式，用 CDP 精确测量每行文字真实渲染宽度后代入计算；手机/平板条带（1024~1249px 这段新纳入的宽度）的横向摆动幅度也同步从固定 px 改成按视口宽度自适应。

### 2. 遇到的错误
- 无实质性错误，但过程中发现：上一轮"按 1366px 换算成 vw"的公式，虽然解决了"会不会裁切"的问题，却没解决"有没有用满可用空间"的问题——因为换算出来的 vw 系数（约 2%~4%）远小于可用空间（margin）随宽度增长的速度（约 50%），宽屏下二者差距会越拉越大。这类问题不会在"是否裁切"的检查里被发现，需要专门去量"用了多少可用空间"才能发现。

### 3. 错误的原因和解决方案
- 原因：见上，本质是"给一个会随宽度变化的目标量（可用空间）配了一个几乎不随宽度变化的供给量（固定小比例的 vw）"，差距只会越拉越大。
- 解决方案：改成直接以"可用空间本身"为基准的公式——`FRACTION × max(0px, 可用空间 - 该行文字真实宽度 - 该行摆动幅度 - 缓冲)`，其中可用空间 `50% - 430px` 本身就是随视口宽度线性变化的量，公式因此天然跟着可用空间等比例伸缩；`FRACTION`（每行 0.33~1，取自原来的相对深度排序）保留了原本"有的行浅、有的行深"的散点错落感，深度为 1 的行会在任意宽度下都紧贴视口边缘。改用 CDP 精确测量每行文字的真实渲染宽度（而不是估算），公式的安全边界因此可以精确核算，不需要再靠经验值预留很宽的冗余。
- 验证时新增了一个"离视口边缘还剩多少像素"的指标（而不是只看"是否裁切"），确认这个数值现在稳定维持在 40~115px 之间（原来在 2560px 下能到 500px+），证明真正解决了"留白"问题而不只是"不裁切"。

### 4. 下一步计划
- 无遗留问题。以后设计"某个元素要不要占满一块可用空间"这类布局时，验证除了要看"有没有超出边界"，还要专门量一下"实际用掉了多少、剩下多少"，两者是不同的检查项。
